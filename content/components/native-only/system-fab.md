# system-fab

The native half of the shared FAB.dsx wrapper has no Web renderer, and is not asked for one: FAB.dsx gates this tag off web, Windows and Linux and gives those lanes a pressable composition instead, so the floating action button an author writes as `<FAB>` is a real, styled, accessible control on every renderer while this tag itself stays native.

## Usage

```dsx
<system-fab icon="plus" aria-label="New" on:tap="dsx.event('new')"/>
```

`system-fab` takes no children.

**Known limits on the web**

- No DOM lookalike of the SwiftUI Button or the Material 3 FloatingActionButton is mounted, so nothing here is reported as a working floating action button.
- The census row records what already ships on the two native lanes; it grants the Web renderer nothing.

**Fallback.** An author who writes `<FAB>` gets the wrapper's own web branch, a pressable carrying the dsx-fab class with the same icon, accessibility label and tap event. A document that writes the native tag directly mounts the honest dsx-unsupported placeholder, a labelled marker carrying the `<system-fab>` name; never blank, never a fake lookalike.

**Implementation notes.** The native half of the shared FAB.dsx wrapper, and the two lanes agree on the whole contract because both read the same three words and the same two numbers. What differs is the platform identity underneath: SwiftUI owns the Button interaction, focus and activation on Apple, while Material 3 owns the visual, ripple, elevation and focus on Android, where the composable also collapses the FAB into one truthful accessibility node so the export is not a nameless clickable plus a raw glyph. The size and icon size are read from the resolved width, height and font size rather than hardcoded, which is why they are recorded as the builder's fallbacks.
